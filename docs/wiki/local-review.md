# Local review

On 2026-11-16 the maintainer decided that the app reviews a local change set, the code the reviewer's own agents write in their clones before it is a PR, the way it reviews a PR. The spec is GitHub issue #104. This page keeps the decisions and why, as the code stands on 2026-11-27.
## Decisions

- **What is reviewed: the branch since the default branch, plus what is not committed.** A local change set is every commit on the branch that is not on the repo's default branch (from their merge base), plus the uncommitted and untracked files git does not ignore. That is what a PR from the branch would show, plus the work not yet in a commit, and whether a commit was pushed changes nothing. The default branch is `refs/remotes/origin/HEAD` as the clone knows it, else `main`, else `master`; no fetch at open, so a local review never needs the network.
- **Started with `guided-review open .` or from the PR switcher.** `open` takes any path inside a clone, worktrees included, and resolves it to the folder's current branch. The switcher lists local change sets of the clones the app knows and of the folders herdr agents work in, beside the PRs. One verb, two doors, as for a PR.
- **Basic first.** A local review opens as a basic tour at once, with no AI. Write guided tour works as for a PR, and read ticks carry to the guided tour. Most local changes are small, and the reviewer reads them while the agent waits.
- **Comments stay local and are tasks for the agent, per comment.** Each comment is Add to tasks (queued, handed over with the others by Send tasks at the finish) or Send now (to the agent at once), mirroring Add to review and Comment now on a PR. Small notes wait for the whole picture; an urgent one goes at once. Nothing half-done reaches GitHub.
- **The agent is the one already in the folder, else one is started.** The terminal that ran `guided-review open` when it runs Claude, else the only Claude terminal working in the folder, else the reviewer picks among several, else the app starts one there as it starts a tour agent. The agent that wrote the code fixes it with its context intact. It is claimed by the herdr label `gr.local=<subject key>`, never a stored terminal id, as `gr.pr=<url>` is for a PR. Write guided tour goes to the same agent (idle: typed in; busy: waits; none: one is started; several: the reviewer picks) and never replaces it.
- **A snapshot, kept as a commit object by a never-pushed ref.** At open and at Update the app writes a commit of the working tree from a temporary index, with `HEAD` as parent, and keeps it from `git gc` with one ref per review, `refs/guided-review/local-<12 hex of the subject key's hash>`. The reviewer's index, working tree, branches and stash are never touched, and since the snapshot is an ordinary commit every reader of git objects (pieces, outline, show, re-pin, check) works on it unchanged. The ref lies outside `refs/heads` and `refs/tags`, so `git push`, `--all` and `--tags` never send it, and the `local-` prefix keeps it from matching a PR's fetch ref, which is all digits. **Known exception:** `git push --mirror` sends every ref, this one too. A snapshot is dated as the `HEAD` it was made over, so the same files over the same `HEAD` are the same commit whoever makes it.
- **Changed on disk, with Update; never live.** What the reviewer reads never moves under them. When the branch gets commits or files change, the sidebar says "Changed on disk" and Update re-pins the tour to a new snapshot as Update tour does after new commits on a PR. A commit of what was uncommitted keeps every tick, since the tree is the same.
- **Move to PR.** When a PR is opened from the branch, the app offers to move the local review to it: read ticks carry by the re-pin rule, open local comments become draft comments in the PR's review that the reviewer sends or drops, resolved ones are dropped, and the local review goes after the PR's state is saved. Nothing reaches the PR's readers without the reviewer's say. Carrying open tasks over as agent threads (see [agent-threads.md](agent-threads.md)) is open.
- **No fake PR URL.** What a review reads is a domain value, the review subject: a PR or a local change set. A local review never pretends to be a PR, so every PR-only feature (reviewing mark, last review, PR notes, viewed sync, GitHub threads, open on GitHub, clone offer, GitHub outage) is decided by the subject's type and cannot reach a local review by mistake.

## In the code

- `review_subject::ReviewSubject` is `PullRequest(PullRequestUrl)` or `Local(LocalChangeSet)`. Its subject key is a PR's URL, so no tour file, state file, app state entry or herdr label of a PR changed when reviews were keyed by subject (#105). `PullRequestUrl` stays only in the host ports and the jobs that call them. A local key is `local:<folder>@<branch>`; the folder escapes `%` and `@` (`%25`, `%40`) and the first `@` ends it, since branch names hold `@` (dependabot's `@types/...`) more often than clone folders do. Every CLI command that takes a review subject takes a `local:` key.
- `ChangeTips` (base branch tip, head) serves both kinds; a local change set's tips are `(base, snapshot)`.
- `local_work_tree::LocalWorkTree` finds the default branch, makes the snapshot and keeps it. A local review is built beside a PR's with `LocalGit` on the folder as its code source and `viewer::NoHost` as its code host, which refuses every call but the look-up of its branch's PR. The window title, the title-bar chip (no GitHub button) and the sidebar's first line come from `Review::window_title` and `local_heading`.
- Reopening a review that has a tour on disk never takes a new snapshot: `OpenedChangeSet::make_basic_tour_if_no_tour` returns at once, and `open_review` reads the code at the tour's pinned snapshot, however the folder has moved on. The overview facts (`LocalFacts`: commits, committed and uncommitted files) are computed from git for that snapshot each time and never stored.
- `check` pins an unpinned guided tour to the snapshot the shown tour reads, so ticks carry at the same head; `refresh` and `tour-path` take the key.
- **Changed on disk** is the work kind `CheckWorkingTree` (on focus, then every 30 s). It asks `CodeSource::change_set_on_disk`, which only a local review's `LocalGit` answers, for an `OnDisk`: `Same`, `Changed` (another `HEAD` than the snapshot was made over, or other files), `OnAnotherBranch` (no Update: the review is of its branch) or `BranchGone` (Drop review; also when the folder is gone). Files are compared with an index of the snapshot's own (`read-tree`, `update-index --refresh`, `diff-files`, `ls-files --others`), so the check writes no objects. That index, and the one a snapshot is made from, live in the system's temp folder, so nothing is written under `.git` but the snapshot's objects and ref. The outcome also sets the working copy, so code links carry "lines may differ" exactly while the folder is not the snapshot. A look that fails is the problem `FolderNotLookedAt` until one goes through.
- **Update and `repin local:...`** run `OpenedChangeSet::repin_to_new_snapshot`: a new snapshot commit, `repin_tour` of the shown tour and a re-pin of the guided tour waiting beside it (pinned ones only, no state of its own), and only then the ref moves, so the ref never lets go of the commit the tour on disk reads. The first open, Update, `repin` and Drop review of one review hold the lock file `<tour>.json.pin.lock` beside the tour from start to end, so a second Update or open cannot save its tour between the first one's tour and ref. An Update in the app and a `repin` from the CLI at once agree on the snapshot.
- **Drop review** deletes the ref first, then the tours, the tour writer's files and the state file: the clean-up on start finds a clone only through a local tour still in it, so a drop that stops part way must leave files to drop again rather than a ref nothing finds. The review refuses changes from the click on (`ReplacingJob::DropReview`, `writes_here_again` if it fails), and `ReviewStateFile` refuses to write a local review's state while none of its tours is on disk, so a copy of the review open elsewhere never puts the state file back. The window shows the switcher in its place.
- **Clean-up on start** deletes `refs/guided-review/local-*` refs that no local review on disk names, in the clones the local reviews on disk name, grouped by repository and not by worktree folder (`LocalWorkTree::shared_git_folder`, `git rev-parse --git-common-dir`). Linked worktrees share one `refs/`; grouping by folder made each worktree's pass delete its siblings' refs, so on 2026-11-17 every start deleted the refs of reviews open in two worktrees of one repository, and the next open dropped the review as "dropped or moved to a PR" and, with no window open, ended the app. A clone with a local tour it cannot read keeps all its refs, as that tour may be the review a ref keeps, and one in the folder of no readable review, whose repository it cannot tell, keeps every repository's refs. `clean_snapshot_refs` says so on stderr, and every review that opens raises the problem `LocalToursNotRead` naming each such tour. Deleting a ref of a folder no longer on disk is a no-op; any other git failure is an error, never "already gone".
- **Threads.** A review's threads live at a `ThreadHome`: GitHub for a PR, the state file's `local_threads` section for a local review, behind `LocalThreadStore`. Comment, thread action, thread read and `agent-reply` run against the home, so the page, placement and outdated following do not know the kinds. The section has one writer path, a locked read and write per change (`ReviewStateFile::update_if`), and the review's own saves never write it, so `agent-reply` writes the answer on the thread itself even while the app shows the review, and neither can write a stale copy over the other's words (guarded by `local_tasks::the_app_and_agent_reply_never_write_a_stale_thread_over_each_others_words`). A local thread keeps the snapshot its lines belong to. Update follows every local thread to the new snapshot once, keeping what the lines said before (`LocalThreadStore::follow_to`, run by `repin_tour`), so no thread needs the old snapshot once `git gc` takes it; a thread whose lines cannot be followed (its file is gone) stays on the old snapshot and shows after the code. `PullThreads` runs on focus for a local review too, reading the state file (`threads_and_followed_at`), which is what shows an answer `agent-reply` wrote from another process while the window was behind.
- **Send actions** are `SendMode`s (`Review::send_modes`: `AddToTasks`, `SendNow`), one button per mode. A task always reaches the agent and carries no seen mark. Send now waits as a draft while the agent link is off; Add to tasks queues all the same, since it hands nothing over yet. A queued task is a local thread (or a reply in one) plus a hand-off in the state `WaitingForSendTasks`, so edit and delete are the thread's own actions and a restart keeps it. Send tasks touches only the review's hand-offs: it takes each task's text and thread as the review last read them (an edit counts), orders them by the reading order of the screen they were sent from and their line, queues them as one batch, and delivery types the batch into the agent as one message, each task under its own id. Because it writes no thread, no stale save or `agent-reply` can lose a task, thread or answer (guarded by `local_tasks::sending_tasks_while_the_agent_answers_another_loses_no_task_thread_or_answer`). A queued task whose comment the review's threads do not show yet stays queued.
- The finish of a local review is `FinishAction::SendTasks`: the sidebar shows "Send tasks (n)" in place of the finish dialog, the end card and the palette say Send tasks, and there is no verdict, approve warning or body.
- **Move to PR.** `PrMover::carry` keeps each snapshot a moved file or step was read at (for "changed since") with a ref of the PR's own, `refs/guided-review/read-<12 hex of the PR key's hash>-<sha>`, in the change set's clone, and the PR's state file names that clone (`read_heads_kept_in`); refs and record are written under the state file's lock. Each open of the PR's review deletes the refs of heads no tick or read-before mark names any more, and forgets the clone once none is left (`let_go_of_unread_snapshots`), so `git gc` takes a snapshot only once the review no longer reads at it. The `read-` prefix never matches `local-`, so the clean-up on start leaves these refs be.
- **Branch link** (`viewer::branch_link::BranchLink`) is the one value a review keeps of the other side of Move to PR: a local review's PR as the host said, or a PR review's local reviews on disk (`LocalReviewsOfRepo`, read by `ReviewBuilder`), its head branch's review and the look-up's backoff. `Review::branch_offer` says what is offered (Open PR, Move to PR, Move here), `decline_the_move` declines either side's offer and the move job starts either side's move from it. A rebuilt review carries it whole. A decline goes to the local review's `declined_moves` only through `ReviewStateFile::decline_move_to`, which the review's own saves never write.
- **`opened_subject::OpenedSubject`** is the one place that tells a PR from a local change set for opening and moving a tour: the code `outline`, `show` and `check` read (a PR's live tips, a local review's pinned snapshot), `code_at` a pin for `refresh`, `make_basic_tour_if_no_tour`, `repin`, and the app's open (`open_review`) with its code source picker and host port. It wraps a private enum of two adapters: the PR one and `OpenedChangeSet`, which alone moves the snapshot ref, under the tour-and-ref lock (`LocalWorkTree::keep_snapshot` and `forget_snapshot` are `pub(crate)` for that reason). It is an enum and not a trait: the set is closed, no test fakes an adapter (tests run real git), and the local adapter keeps calls of its own (drop, facts). The app's Update goes through `update_shown_tour`, which takes the app's ports so tests put fakes behind them. Where an agent works is `ReviewSubject::own_folder` for a local change set; for a PR it differs on purpose: the tour writer looks for a clone (`opened_subject::writer_folder`), the opened review's agents work in its code source's clone, and the app's own open of a PR starts from the folder its state file remembers, which need not be a clone.

## A missing snapshot ref is a problem the reviewer sees (#125, 2026-11-17)

`refuse_when_gone` used to take any tour with no snapshot ref for a review already dropped or moved, delete the tour, and with no window open end the app with the reason only in `app.log`, after the CLI had printed "opened". The cause of the lost ref was fixed in #126; the rules that stay:

- **A drop or a move leaves a record** (`GoneLocalReviews`, one file per review in `gone-local-reviews/` of the state folder, named as its snapshot ref; written by `drop_review` before the ref goes, so a drop that stops part way still reads as on purpose). Starting the review again (`make_basic_tour_if_no_tour`) forgets it. With a record, a tour that turns up after the drop is deleted; without one the ref was lost: the open fails with a reason that says what is lost and what to do (Drop review in the switcher, then `guided-review open <folder>`), and the tour and the reviewer's notes stay.
- **A failed build with no window opens the switcher** with the reason under the query (`FailedBuild::OpenSwitcherWithReason`), the window `Relaunched::OpenSwitcherOnly` already gives a Dock click, in place of ending the app. Closing it ends the app as for any switcher-only window.
- **`open` waits for the build.** `OpenRequest.waits_for_build` (set by the CLI; an app from before it ignores the field) makes the app answer when the build ends: `Opened`, or `Refused` with the reason, which the CLI prints and exits non-zero on; after 60 s the answer is `StillOpening` and the build goes on. A superseded build answers `Refused`. An older app answers `Opening` at once, and the CLI then says an older build runs and to quit it (it never quits it itself, per "a command never quits an app of another build"); an app that closes the connection without answering gets the same message instead of `EOF while parsing`. An older CLI against this app gets `Opening` at once.

## Known open

- The CLI's `repin` (PR or local) while the app shows the same review leaves the app's copy of the review stale until it is updated or reopened; a tick in it meanwhile writes its stale ticks over the re-pin's record, as for a PR today.
- Reviews dropped before #125 have no record, so one of them with a stray tour now reads as lost and is kept for the reviewer to drop.
