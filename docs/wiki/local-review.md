# Local review

On 2026-11-16 the maintainer decided that the app reviews a local change set, the code the reviewer's own agents write in their clones before it is a PR, the way it reviews a PR. The plan is the spec in GitHub issue #104; this page keeps the decisions and why. It supersedes the "Decided for the later review of local changes" section of [Basic mode](basic-mode.md).

## Decisions of 2026-11-16

- **What is reviewed: the branch since the default branch, plus what is not committed.** A local change set is every commit on the branch that is not on the repo's default branch (from their merge base), plus the uncommitted and untracked files git does not ignore. That is what a PR from the branch would show, plus the work not yet in a commit, and whether a commit was pushed changes nothing. The default branch is `refs/remotes/origin/HEAD` as the clone knows it, else `main`, else `master`; no fetch at open, so a local review never needs the network.
- **Started with `guided-review open .` or from the PR switcher.** `open` takes any path inside a clone, worktrees included, and resolves it to the folder's current branch. The switcher lists local change sets of the clones the app knows and of the folders herdr agents work in, beside the PRs. One verb, two doors, as for a PR.
- **Basic first.** A local review opens as a basic tour at once, with no AI; Write guided tour works as for a PR, and read ticks carry to the guided tour. Most local changes are small, and the reviewer reads them while the agent waits.
- **Comments stay local and are tasks for the agent, per comment.** Each comment is Add to tasks (queued, handed over with the others by Send tasks at the finish) or Send now (to the agent at once), mirroring Add to review and Comment now on a PR. Small notes wait for the whole picture; an urgent one goes at once. Nothing half-done reaches GitHub.
- **The agent is the one already in the folder, else one is started.** The terminal that ran `guided-review open` when it runs Claude, else the only Claude terminal working in the folder, else the reviewer picks among several, else the app starts one there as it starts a tour agent. The agent that wrote the code fixes it with its context intact. It is claimed by the herdr label `gr.local=<subject key>`, never a stored terminal id, as `gr.pr=<url>` is for a PR.
- **A snapshot, kept as a commit object by a never-pushed ref.** At open and at Update the app writes a commit of the working tree from a temporary index, with `HEAD` as parent, and keeps it from `git gc` with one ref per review under `refs/guided-review/`. The reviewer's index, working tree, branches and stash are never touched, and since the snapshot is an ordinary commit every reader of git objects (pieces, outline, show, re-pin, check) works on it unchanged. The ref lies outside `refs/heads` and `refs/tags`, so `git push`, `--all` and `--tags` never send it. **Known exception:** `git push --mirror` sends every ref, this one too.
- **Changed on disk, with Update; never live.** What the reviewer reads never moves under them. When the branch gets commits or files change, the sidebar says "Changed on disk" and Update re-pins the tour to a new snapshot exactly as Update tour does after new commits on a PR. A commit of what was uncommitted keeps every tick, since the tree is the same.
- **Ticks carry to guided.** As for a PR's basic tour.
- **Move to PR.** When a PR is opened from the branch, the app offers to move the local review to it: read ticks carry by the re-pin rule, open local comments become draft comments in the PR's review that the reviewer sends or drops, resolved ones are dropped, and the local review goes after the PR's state is saved. Nothing reaches the PR's readers without the reviewer's say.
- **No fake PR URL.** The app names what a review reads with a domain value, the review subject: a PR or a local change set. A local review never pretends to be a PR, so every PR-only feature (reviewing mark, last review, PR notes, viewed sync, GitHub threads, open on GitHub, clone offer, GitHub outage) is decided by the subject's type and cannot reach a local review by mistake.

## In the code

- `review_subject::ReviewSubject` is `PullRequest(PullRequestUrl)` or `Local(LocalChangeSet)`. Its subject key is a PR's URL, so no tour file, state file, app state entry or herdr label of a PR changed when the review was keyed by the subject instead (#105). `PullRequestUrl` stays only in the GitHub ports and the jobs that call them.
- A local key is `local:<folder>@<branch>`. The folder escapes `%` and `@` (`%25`, `%40`) and the first `@` ends it, since branch names hold `@` (dependabot's `@types/...`) more often than clone folders do.
- `ChangeTips` (base branch tip, head) was `PullRequestTips`; a local change set has the same two tips, `(base, snapshot)`.
- Until the later tickets of #104, the CLI refuses a `local:` key with "local review is not built yet" for the commands not built for it yet (now only `agent-reply`).
- #111 built Write guided tour: the writer task goes to the change set's agent (idle: typed in; busy: waits; none: one is started in the folder; several: the reviewer picks), never replacing it. `check` pins an unpinned guided tour to the snapshot the shown tour reads, so ticks carry at the same head; `refresh` and `tour-path` take the key. The switch and the reload give the rebuilt review its facts again, and Changed on disk goes on since the check job comes from the subject.
- #106 built the local open: `local_work_tree::LocalWorkTree` finds the default branch (`refs/remotes/origin/HEAD`, else `main`, else `master`), makes the snapshot from a temporary index and keeps it at `refs/guided-review/local-<12 hex of the subject key's hash>`. The `local-` prefix keeps it from ever matching a PR's fetch ref, which is all digits.
- Reopening a review that has a tour on disk never takes a new snapshot: `OpenedChangeSet::make_basic_tour_if_no_tour` returns at once, and `open_review` reads the code at the tour's pinned snapshot, however the folder has moved on. The overview facts (`LocalFacts`: commits, committed and uncommitted files) are computed from git for that snapshot each time and never stored.
- `open_review` builds a local review beside a PR's: its code source is `LocalGit` on the folder, and its GitHub port is `viewer::NoGitHub`, which refuses every call. The window title, the title-bar chip (no GitHub button) and the sidebar's first line come from `Review::window_title` and `local_heading`.
- #107 built Changed on disk. The work kind `CheckWorkingTree` (on focus, then every 30 s) asks `CodeSource::change_set_on_disk`, which only a local review's `LocalGit` answers, for an `OnDisk`: `Same`, `Changed` (another `HEAD` than the snapshot was made over, or other files), `OnAnotherBranch` (no Update: the review is of its branch) or `BranchGone` (Drop review; also when the folder is gone). The files are compared with an index of the snapshot's own (`read-tree`, `update-index --refresh`, `diff-files`, `ls-files --others`), so the check writes no objects; that index, and the one a snapshot is made from, live in the system's temp folder, so nothing is written under `.git` but the snapshot's objects and ref (2026-11-17). Its outcome also sets the working copy, so code links carry "lines may differ" exactly while the folder is not the snapshot. A look that fails is the problem `FolderNotLookedAt` until one goes through.
- Update and `repin local:...` run `OpenedChangeSet::repin_to_new_snapshot`: a new snapshot commit, `repin_tour`, and only then the ref moves, so the ref never lets go of the commit the tour on disk reads. The Update reads the overview facts again for the new snapshot. A snapshot is dated as the `HEAD` it was made over, so the same files over the same `HEAD` are the same commit whoever makes it: an Update in the app and a `repin` from the CLI at once agree on it. The first open (`make_basic_tour_if_no_tour`, which looks for a tour only once it holds the lock), Update, `repin` and Drop review of one review hold the lock file `<tour>.json.pin.lock` beside the tour from start to end, so a second Update or open cannot save its tour between the first one's tour and ref (2026-11-17).
- Drop review deletes the ref first, then the tours, the tour writer's files and the state file (2026-11-17): the clean-up on start finds a clone only through a local tour still in it, so a drop that stops part way must leave files to drop again rather than a ref nothing finds. The review refuses changes from the click on (`Review::start_drop`), and `ReviewStateFile` refuses to write a local review's state while none of its tours is on disk, so a copy of the review open elsewhere never puts the state file back. The window shows the switcher in its place. On each start the app deletes `refs/guided-review/local-*` refs that no local review on disk names, in the clones the local reviews on disk name; a clone with a local tour it cannot read keeps all its refs, as that tour may be the review a ref keeps, and `clean_snapshot_refs` says so (printed to stderr). Every review that opens raises the problem `LocalToursNotRead` naming each such tour, so the reviewer learns of it (2026-11-17). Deleting a ref of a folder no longer on disk is a no-op; any other git failure is an error, never "already gone".
- **Known open:** the CLI's `repin` (PR or local) while the app shows the same review leaves the app's copy of the review stale until it is updated or reopened; a tick in it meanwhile writes its stale ticks over the re-pin's record, as for a PR today.
