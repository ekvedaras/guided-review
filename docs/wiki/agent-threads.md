# Agent threads and the Ask panel's removal

2026-11-27. The maintainer replaced the Ask panel with a private thread to the tour agent. The code is in the commits "Remove the Ask panel", "Rename the comment-and-hand-off action" and the one that adds Ask agent; this page records the decisions and what stays open.

## Decisions (maintainer, 2026-11-27)

- The Ask panel is gone: its `A` key, palette action, the `asks` state section, `ask_model` and `ask_effort` with their Settings section, the Ask scene, `ClaudeCli` and the agent ports only it used. Old state files keep an `asks` key as an unknown section (kept, never read). A `[keys]` line `ask_about_step` is now an unknown name, reported once like any other (open: it could be ignored silently).
- The action that posts to GitHub and hands the comment to the tour agent is **Comment and ask agent** (and **Comment and ask agent now**). The old config values (`primary_comment_action`, `secondary_comment_action` = `ask_agent`, `ask_agent_now`) and the `[keys]` entries of those names keep their old meaning (`SendAction::former_config_text`, `Command::former_config_name`). Settings writes the new names.
- **Ask agent** is the new action for the tour agent alone, in PR mode, on lines or a file (`CommentPlace`), sending now only: no task queue for a PR. The thread is kept in the state file and the tour agent answers into it with `agent-reply`.
- A thread's home is a property of the thread. A PR review holds GitHub's threads and agent threads side by side.
- It looks like a normal thread with a small "Not on GitHub" chip. Scene `100-agent-thread`.
- Ask why with no review agent alive goes to the tour agent (research Q5a).
- Move to PR of a local review's tasks is unchanged: open tasks still become draft comments for GitHub. Open question: carry them as agent threads instead.

## What the agent decided

- Config text of the new action is `ask_agent_only`, since `ask_agent` has to keep meaning Comment and ask agent. Default key `Cmd+Alt+P`; no other action stands in for it (a box without it falls back to Add to review, never to an action that posts).
- A thread's home is told by its id: the ids `LocalThreads` gives start with `local-`, no host's do (`ThreadId::is_private`). `ThreadHomes` (`local_thread_store.rs`) picks the home of a thread, of a comment and of a new thread (a task mode, `SendMode::SendNow`, is private; in a PR it is the only one). A PR's send modes are Add to review, Comment now and Send now.
- One read job (`PullThreads`) reads every home and merges; the outcome of a send or a thread action replaces only its own home's threads (`ReviewCore::set_threads_of`). Open: when the host does not answer, the whole read fails, so agent threads do not show until it does; threads already shown stay.
- The message the agent is typed for a private question starts `Private question hN on <pr>`, says `Not on GitHub`, carries the code, the thread so far and `Question:`, and answers like a PR comment except that nothing is posted and no 👀 goes on a comment (`HandOff::private_message`). `agent-reply` finds the home from the hand-off's thread, so the same command writes the answer to the state file and says so (`ReplyPlacement::KeptOnThread`).
- Ask why on a finding with no review agent: the question and the finding, quoted, go into a comment box on the finding's lines, which the session sends as an Ask agent question. A finding on the whole change has no lines, so the question is refused with a reason. The finding stays open.
- `SelectedLines` no longer hands out its rows; its three callers ask for head texts, the text told to an agent, or numbered texts. This cleared a field leak the removal had made.
- The deslop allow lists lost 6 entries (the Ask desk's) with the removal, the tangle key naming `comments_and_asks` was renamed to `comments_here`, and the agent thread work cut 8 more: `agent_reply` takes the homes as a closure (`ThreadHomes::agent_reply` wraps it), so `HandOffs` does not name `ThreadHomes`; the snapshot staging of local tasks left `LocalThreadStore` (`local_task_staging.rs`); the text box keeps its sending keys in one `SendKeys`. The `hand_offs` / `local_thread_store` / `review_state` tangle is smaller but still allowed: `AgentReplyRequest` holds a `ThreadHome`, which holds a store of the state file that holds the hand-offs.

## The private answer that went to GitHub (2026-11-27)

The maintainer asked a private question on a PR of a private repo with build 17542fde. The tour agent got `Private question h2`, ran `guided-review agent-reply <pr> h2 --working` and `--body -`, and the reply failed trying to post on GitHub.

- Cause: the agent ran the release install, not the build that wrote the hand-off. The agent was the maintainer's own Claude, picked as the tour agent, and `guided-review` on its `PATH` is `~/.local/bin/guided-review`, release 0.16.0 (3df2bed). That build picks a reply's home from the review subject (`ThreadHome::of(subject)`), so for a PR it posts every reply on GitHub, here to thread `local-thread-1`. The state file was right: hand-off `h2` held thread `local-thread-1`, the private thread. The PATH fix for agents the app starts (agent-runs.md, 2026-11-16) does not reach a terminal the reviewer picked.
- The commands the private question's message gives, run as the CLI, write the answer into the private thread and ask GitHub nothing: `agent_threads::the_commands_the_private_question_gives_the_agent_write_its_answer_into_the_private_thread` takes them from the message the fake agent got. Red when `ThreadHomes::of_thread` names the host for every thread, with the maintainer's error.
- `check` and `open` in the same message touch the tour, not threads.
- Found on the way: a PR offered Hand to agent on the agent's own answer in a private thread, since that answer is not the reviewer's. The hand-off would have told the agent it was a GitHub comment and tried a 👀 on GitHub with a local comment id. Now `HandOffs::hand_over_refused` is the one rule for the button and for `hand_over`, and refuses a private thread (`HandToAgentRefused::PrivateThread`); the reviewer replies in the thread instead. Test `agent_threads::the_agents_answer_in_a_private_thread_is_not_handed_to_the_agent_as_someone_elses_comment`.
- Open: once this branch is released, the release install answers private questions. Until then, and for every later change to what `agent-reply` or `fix-reply` does, a picked tour agent runs the release and not the trial build. Two ways out, not decided: (a) the messages to the tour agent name the running binary's full path when the app is not the release install; this needs the app-started agents' `--allowedTools` (`claude_cli.rs`, `Bash(guided-review agent-reply:*)`) to allow that path too, and does not reach the commands the tour skill names. (b) A reply command run by another build than the app's hands itself to the app's build; this helps only from the release that has it.

## A trial build names itself to agents (2026-11-27)

The maintainer picked way (a) of the open item above: when the app is not the release install, every message it types into an agent names the running binary by its full path for guided-review commands, and the agents it starts may run it.

- `AgentCli` (`src/agent_cli.rs`) is the one place that decides: `OnPath` (`guided-review`) when `running_build()` is the release, else `At(<running binary>)`, shell-quoted when the path needs it. Every message builder writes its commands as `{cli} <command>` and takes the value from the agents it goes to: `TourAgentPort::agent_cli`, read through `TourAgents::agent_cli` and `ReviewAgents::agent_cli`. The herdr adapter decides it once (`HcTourAgents::new`), beside the `PATH` it gives the agents it starts, since both are how an agent in herdr reaches the app's build. The fakes say `OnPath` unless a test asks for a trial build (`FakeTourAgent::of_a_trial_build`).
- Hand-offs, fix requests and Ask why questions are now written when they go (`DeliveryRequest`, `FixDeliveryRequest` and `WhyDeliveryRequest` hold the hand-offs, fix requests or questions, not the text), because `ReviewCore`, which makes the request, does not know the agents. The reviewer's own words and the quoted code are never rewritten: the path goes only where the builder writes a command.
- The tool lists of the agents the app starts (`tour_skill_tools`, `tour_agent_tools`, `review_agent_tools`) allow every guided-review command both by name and by the path (`AgentCli::bash_rules`). By name stays, since the tour skill names its commands so, and on such an agent's `PATH` the build comes first (agent-runs.md, 2026-11-16).
- The tour skill is not changed. A task that runs it (writing a tour, a Refresh) adds "Run every `guided-review` command the skill names as `<path>`" to the skill's brief, so a subagent gets it too.
- `guided-review review-brief` names the binary that printed it the same way (`ReviewBrief::running_guided_review_as`), since the review agent ran that one by its path.
- Tests: `*::a_trial_build_names_itself_*` in `agent_threads`, `agent_refresh`, `basic_hand_offs`, `tour_writing`, `review_agents`, `fix_requests`, `ask_why`, `local_tasks` and `review_skill`; `hc_tour_agent::the_agents_of_a_trial_build_may_run_it_by_its_full_path_and_by_name`; `agent_cli::*`.
- Open: the CLI's own hints that an agent may read (`outline`'s small-PR line naming `guided-review show`, the repin and `open` errors) still say `guided-review`. `guided-review eval`'s writer (`ClaudeEvalWriter`) is run from a terminal, not by the app, and is unchanged. Not tried on a live picked agent.
