# Agent threads and the Ask panel's removal

2026-11-27. The maintainer replaced the Ask panel with a private thread to the tour agent. How the app starts and finds agents is in [agent-runs.md](agent-runs.md).

## Decisions (maintainer, 2026-11-27)

- The Ask panel is gone: its `A` key, palette action, the `asks` state section, `ask_model` and `ask_effort` with their Settings section, the Ask scene, `ClaudeCli` and the agent ports only it used. Old state files keep an `asks` key as an unknown section (kept, never read). A `[keys]` line `ask_about_step` is now an unknown command name, reported once like any other (`KeyProblem::UnknownCommand`). Open: it could be ignored silently.
- The action that posts to GitHub and hands the comment to the tour agent is **Comment and ask agent** (and **Comment and ask agent now**). The old config values (`primary_comment_action`, `secondary_comment_action` = `ask_agent`, `ask_agent_now`) and the `[keys]` entries of those names keep their old meaning (`SendAction::former_config_text`, `Command::former_config_name`). Settings writes the new names.
- **Ask agent** is the new action for the tour agent alone, in PR mode, on lines or a file (`CommentPlace`), sending now only: no task queue for a PR. The thread is kept in the state file and the tour agent answers into it with `agent-reply`. Its config text is `ask_agent_only`, since `ask_agent` has to keep meaning Comment and ask agent. Default key `Cmd+Alt+P`. No other action stands in for it: a box without the key falls back to Add to review, never to an action that posts.
- A thread's home is a property of the thread. A PR review holds GitHub's threads and agent threads side by side. The home is told by the id: the ids `LocalThreads` gives start with `local-`, no host's do (`ThreadId::is_private`). `ThreadHomes` (`local_thread_store.rs`) picks the home of a thread, of a comment and of a new thread (a task mode, `SendMode::SendNow`, is private; in a PR it is the only one). A PR's send modes are Add to review, Comment now and Send now.
- A private thread looks like a normal thread with a small "Not on GitHub" chip. Scene `100-agent-thread`.
- One read job (`PullThreads`) reads every home and merges. The outcome of a send or a thread action replaces only its own home's threads (`ReviewCore::set_threads_of`). Open: when the host does not answer, the whole read fails, so agent threads do not show until it does; threads already shown stay.
- Ask why on a finding goes to the review agent when one is alive, else to the tour agent (research Q5a). For the tour agent, the question and the finding, quoted, go into a comment box on the finding's lines, which the session sends as an Ask agent question. A finding on the whole change has no lines, so the question is refused with a reason. The finding stays open.
- Move to PR of a local review's tasks is unchanged: open tasks still become draft comments for GitHub. Open question: carry them as agent threads instead.

## How a private question runs

- The message typed to the agent starts `Private question hN on <pr>`, says `Not on GitHub`, carries the code, the thread so far and `Question:`, and answers like a PR comment except that nothing is posted and no 👀 goes on a comment (`HandOff::private_message`). `agent-reply` finds the home from the hand-off's thread, so the same command writes the answer to the state file (`ReplyPlacement::KeptOnThread`).
- A PR offers no Hand to agent on a private thread: the agent's own answer there is not the reviewer's comment, and handing it over would tell the agent it was a GitHub comment and try a 👀 on GitHub with a local comment id. `HandOffs::hand_over_refused` is the one rule for the button and for `hand_over` (`HandToAgentRefused::PrivateThread`); the reviewer replies in the thread instead.
- The `hand_offs` / `local_thread_store` / `review_state` tangle is still on the deslop allow lists: `AgentReplyRequest` holds a `ThreadHome`, which holds a store of the state file that holds the hand-offs. `agent_reply` takes the homes as a closure (`ThreadHomes::agent_reply` wraps it), so `HandOffs` does not name `ThreadHomes`.
- `SelectedLines` does not hand out its rows; its callers ask for head texts, the text told to an agent, or numbered texts.

## A reply made by another build went to GitHub (2026-11-27)

The maintainer asked a private question on a PR with a trial build. The tour agent, the maintainer's own Claude picked as the tour agent, ran `guided-review agent-reply` from `~/.local/bin`, the release install (0.16.0). That build picks a reply's home from the review subject (`ThreadHome::of(subject)`), so for a PR it posts every reply on GitHub, and failed on thread `local-thread-1`. The state file was right. The `PATH` fix of agent-runs.md reaches only agents the app starts.

- The commands the private question's message gives, run as the CLI, write the answer into the private thread and ask GitHub nothing (test `agent_threads::the_commands_the_private_question_gives_the_agent_write_its_answer_into_the_private_thread`, red when `ThreadHomes::of_thread` names the host for every thread). The `check` and `open` commands in the same message touch the tour, not threads.
- Decided (way (a), over letting a reply command hand itself to the app's build, which helps only from the release that has it): when the app is not the release install, every message it types into an agent names the running binary by its full path for guided-review commands, and the agents it starts may run it. `AgentCli` (`src/agent_cli.rs`) is the one place that decides: `OnPath` (`guided-review`) for the release, else `At(<running binary>)`, shell-quoted when needed. Every message builder writes `{cli} <command>`, taking the value from the agents it goes to (`TourAgentPort::agent_cli`, read through `TourAgents::agent_cli` and `ReviewAgents::agent_cli`). The herdr adapter decides it once (`HcTourAgents::new`), beside the `PATH` it gives the agents it starts. Tests: `*::a_trial_build_names_itself_*`, `agent_cli::*`.
- Hand-offs, fix requests and Ask why questions are written when they go (`DeliveryRequest`, `FixDeliveryRequest`, `WhyDeliveryRequest` hold the items, not the text), because `ReviewCore`, which makes the request, does not know the agents. The reviewer's own words and quoted code are never rewritten.
- The tool lists of agents the app starts (`tour_skill_tools`, `tour_agent_tools`, `review_agent_tools`) allow every guided-review command both by name and by path (`AgentCli::bash_rules`). By name stays, since the tour skill names its commands so.
- The tour skill is unchanged. A task that runs it (writing a tour, a Refresh) adds "Run every `guided-review` command the skill names as `<path>`" to the skill's brief, so a subagent gets it too. `guided-review review-brief` names the binary that printed it the same way (`ReviewBrief::running_guided_review_as`).
- Open: the CLI's own hints that an agent may read (`outline`'s small-PR line naming `guided-review show`, the repin and `open` errors) still say `guided-review`. `ClaudeEvalWriter` is run from a terminal, not by the app, and is unchanged. Not tried on a live picked agent.
