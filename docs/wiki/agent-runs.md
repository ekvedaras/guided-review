# Agents the app works with

How the app hands work to Claude agents, what went wrong, and what was decided. The private thread to the tour agent is in [agent-threads.md](agent-threads.md). The Mac-load rules for agent builds are in [agent-builds.md](agent-builds.md).

## Lessons that hold

- Exit 0 from an agent proves nothing. Check the outcome the run was meant to produce. The first refresh writer (`claude -p`) was denied a chained shell command, said so, exited 0, and the app showed the old tour with no error (fixed 2026-11-06 in `8030ad0`, `a8cdb64`, `8a99930`). The refresh now checks that the refresh marks are gone (see "Refresh tour").
- An agent with a fixed tool list fails on chained shell commands, since a chained call matches no single-command rule. The tour skill and every first task ask for one command per Bash call. `tests/it/tour_skill.rs` holds every command the skill names to the tool list.
- `hc run` starts a terminal with the herdr server's environment, not the caller's. An agent the app starts runs under `env PATH=<the running guided-review's folder>:<the app's PATH>` (`path_for_agents`, `src/hc_tour_agent.rs`). The folder always goes to the front, once, so a trial build in `~/.cargo/bin` is not hidden by the release install in `~/.local/bin` (2026-11-16). A terminal the reviewer picked keeps its own `PATH`; a trial build names its binary by full path in every message to it (see [agent-threads.md](agent-threads.md), "A trial build names itself to agents").

## Which agent a subject has

- herdr (`hc`) is required for agent features, decided 2026-11-06. There is no hidden `claude -p` fallback for them: one way to talk to agents, and the reviewer can watch or take over any agent in herdr-app. Without herdr the app turns those features off and says why.
- `TourAgents::find` is the one lookup every path asks (writing a missing tour, Write guided tour, Show agent, hand-offs, the sidebar). It takes the terminal with the subject's `gr.pr` label. Else it takes the one Claude terminal, not started by the app, whose folder is in a clone of the PR's repo on the PR's head branch (GitHub's `headRefName`, asked once and kept; a failed look or a fork's PR finds only the label). A local review looks in its change set's folder. Several candidates are offered with "Use this agent". Decided 2026-11-18, because a missing tour's writer once started a fresh agent beside the reviewer's own Claude.
- `open` claims a terminal: the Claude session that ran it; else, when run in a plain shell, a Claude terminal in the same herdr session; else the app starts its own agent. Only a terminal that runs Claude is claimed, and with several Claude terminals in that session none is, since a busy unrelated session would get the PR's questions mid-work (2026-11-06).
- A label outlives the Claude that earned it, since herdr keeps labels after a session ends (#198, 2026-11-26). `TourAgents::still_works_on` therefore checks a labelled terminal on every lookup: it stays the agent while it runs Claude and its folder is in a clone of the PR's repo (any branch, since the agent that opened the PR may switch), or in the local review's folder (`works_in`). An agent the app started, and a terminal herdr does not list, stay. A terminal that fails the check loses the label and `find_unclaimed` looks again. Not covered: another Claude session started later in the same clone keeps the label, since herdr gives no session id (not checked). The integration tests' CLI runner drops `HC_TERMINAL_ID`, so a test run from a herdr terminal never claims it.
- The reviewer can pick by hand (#198): `TourAgents::agent_choices(subject, role)` lists every live Claude terminal with its herdr space (the row's bold word), folder, repo and branch, status, and marks for the subject's tour agent, review agent, and "started by the app". The picker (`agent_picker`) has a search over those words and a Show button per row, and opens from the "Pick the agent" icon on the Tour and AI review stations. Listing changes no label. Picking claims the terminal and takes the label off any other (`ReviewSession::use_tour_agent`; `ReviewAgents::claim` for the review role, which ends nothing). `ReviewAgents::end` kills only review agents the app started and only takes the label off one the reviewer picked. Scene `99-agent-picker`. Open: a new AI review run still starts its own agent and takes the label off the picked one.

## Agents the app starts

- Labels: `herdr.space=guided-review` and `herdr.tab=<terminal name>`, since herdr-app shows only labelled terminals (`ekvedaras/guided-review@1fbdb5a`, `a8bad50`). The adapter then renames the space "guided-review agents" and the tab `owner/repo#N`, retrying for up to 3 s and giving up quietly with no herdr window. Not plain "guided-review": the maintainer's own space of this repo has that name. An app-started agent has `gr.started-by=app`. The cap of app-started agents is 5 (`MAX_APP_AGENTS`; 3 until 2026-11-19). Open: an agent started while the window is closed shows in an unnamed space until Show agent or a later start names it.
- Permission mode is `auto`, not `dontAsk` (2026-11-10, `src/hc_tour_agent.rs`): the agent edits, tests and pushes. It is chosen over `bypassPermissions` to keep auto mode's block on destructive commands, since the agent reads comments and code of other people's PRs. `--allowedTools` lists the calls auto mode allows without its classifier. `dontAsk` remains only in the eval writer (`ClaudeEvalWriter`, `src/claude_cli.rs`).
- Tool lists (`tour_skill_tools`, `tour_agent_tools`, `review_agent_tools` in `src/claude_cli.rs`) carry `Read(//<clone>/**)` and `Read(~/.guided-review/tours/**)`, not a bare Read, plus bare `Grep` and `Glob`. A `Grep(path)` or `Glob(path)` rule is accepted but never applied, so with only those the agent had no Grep or Glob tool at all (tried live 2026-11-06). The cwd is the clone, but a Grep or Glob given another path is not stopped.
- herdr facts the adapter relies on (fixtures in `tests/fixtures/hc/`): `hc events --json` writes a snapshot line, then JSON-RPC lines whose `params.type` is `status` or `turn`. `hc send --if idle` refuses with exit 10 (`kind: status_mismatch`); after a turn herdr reports `done` until someone looks, and the adapter sends plainly when the refusal says `done`, but never to a `working` or `blocked` agent. A terminal still starting refuses with exit 5, `kind: unavailable`; the hand-off stays queued and the app tries again after 3 s. `hc read --lines N` gives N lines of history above the whole screen, not the last N lines, so the loading screen shows the last non-blank lines above Claude's prompt box.
- An `open` from an app-started terminal of a PR not on screen never switches the window; the CLI answers `kept_in_background` (`OpenDecision::KeepInBackground`). Which tours are being written, and which PRs got an agent reply while not shown, are in `app.json` in the state folder (`src/viewer/app_state.rs`), PR urls only. After a restart each writing finds its terminal by the PR's `gr.pr` label, or fails with a reason.

## Writing a tour, and `open` of a PR with no tour

- Writing a missing tour is a task typed to the PR's agent: to the reviewer's own agent when idle (it waits while busy), else to an app-started one under the tool rules above. The writer's own `open` is the only "done" signal. A writer that goes idle after working without it, whose terminal ends, or that could not start fails: the loading screen shows why with the last screen lines, Try again and Show agent, and the switcher row says "writing failed".
- `guided-review open` of a PR with no tour no longer refuses (2026-11-12). The app decides (`ActivePr::open(pr, origin, TourFact)`): one with a tour opens as before, one without goes through `ActivePr::write`, the switcher's path, and the CLI prints "No tour of <pr> yet; guided-review app is writing one and opens it when it is ready". `open` does not check that herdr is reachable first; a writer that cannot start shows as Failed with Try again. `open_review` still refuses a PR with no tour as a last guard.

## Refresh tour

On 2026-11-27 the maintainer decided that Refresh tour is handed to the PR's tour agent, like Hand to agent. It no longer runs `claude -p`.

- `TourAgentRefresh` (`viewer/agent_refresh.rs`) is the `RefreshWriter`. It types the task into the idle agent (`TourAgents::hand_refresh_task`); a subagent runs the skill's Refresh section when the agent already holds a conversation. With no agent the app starts one with the task as its first. Several agents are for the reviewer to pick: the Refresh button opens the picker. A local review's agent is told not to change the code.
- Done is the agent's turn ending, read from its herdr status every 2 s: it has to be seen working, then idle. A busy agent is waited for up to 10 minutes, one that does not start for 60 s (`Pace::real`). `TourRefresher` then checks the outcome: the marks must be gone, else the refresh fails and the sidebar says so.
- The banner's activity line says what the app does (waiting for the agent, the agent is refreshing, it waits for you), not each tool Claude used, since herdr gives a status, not a tool stream.
- The agent's own `open` at the end reloads the review after the Refresh landed, a second, harmless rebuild.
- While a Refresh runs, the banner's button is Cancel. It ends both waits through a `Cancel` the writer's pause wakes on at once, and the refresh lands as `RefreshCancelled`: no failure, the banner idle, the replacing-jobs slot free. The agent is not interrupted and may still finish; its `refresh --done` and `open` then reload the review. The slot frees when the wait ends, not at the click, so a cancelled run's outcome can never land as a later Refresh's. Cancel does nothing once the writer has returned.
- Open: a Refresh while the agent is on a long turn blocks every other replacing job for up to 10 minutes unless cancelled. Not tried on a live agent.

## Comments and hand-offs

- The comment box has two send actions (2026-11-06): "Comment" goes to GitHub for the author with no agent; "Comment and ask agent" (renamed 2026-11-27) goes to GitHub and to the tour agent, which answers on that thread with 🤖. Not every comment goes to the agent, because comments meant for the PR author would get a 🤖 reply under the maintainer's name. The agent Q&A stays on GitHub on purpose, as a lasting trace of the discussion.
- The agent may change code on any PR, not only the maintainer's own (2026-11-10). It reverses the 2026-11-06 rule that it never does, because the maintainer wanted 👀 and "Working on it…" replies for comments that need code changes. It works in its own folder when that is a clone of the repo; else in a cheap worktree. The message and the tour skill add: only when the clone is on the PR's branch with none of the reviewer's own changes, and the agent commits and pushes to the PR's branch.
- The viewer puts the 👀 when the delivery goes through, not the agent, so it cannot be forgotten. `agent-reply --working` posts the reply and the hand-off keeps its comment id; the next `agent-reply --body` edits that comment. Both take the 👀 off. Open: whether GitHub takes a reaction on a comment in a pending review is not tried live; if it refuses, the line under the thread says so.
- A comment by anyone but the reviewer gets Hand to agent (#158, 2026-11-23). The reviewer's click is the instruction, so the app writes the request for them ("The reviewer hands you <login>'s comment to handle for them …"), and the comment, the thread before it and the replies after it stay quoted with `> `. The request limits the agent to what the comment asks of this PR's code and tour. What GitHub hides in the comment (`viewer::HiddenText`) is left out of the message and named in a `Left out of the comment` line. The idea of the app passing new comments to the agent by itself was turned down: others' words would reach the agent with no look from the reviewer (`8c1965c`: every agent reads text from the change as data only). Such a hand-off is saved under its own key (`handed`), so an older build keeps the entry unread (`KeptEntries`) instead of typing it as the reviewer's own words. It is one more hand-off (`hand_offs.rs`): same queue, seen mark, `agent-reply` answer and line under the thread.
- Hidden text is found mechanically: HTML comments outside code, link reference definitions no link or picture uses, and invisible characters (Unicode tag characters outside flag emoji, supplementary variation selectors, direction controls, zero-width characters only from eight on, since fewer cannot spell a letter in binary and a few come with pasted text). A warning line under a comment or PR description shows that text hides, and the text on hover.
- The PR switcher lists every open PR that involves the reviewer plus PRs with their team's review requested, newest update first, with no date limit (2026-11-06).

## The review agent (AI review)

- Its place is `ReviewPlace::choose` (2026-11-23). It starts in the subject's tour agent folder (a local review's change set folder) when that is a git checkout whose HEAD is the reviewed head with an empty `git status --porcelain`, and works there as it is (`TourAgentFolder`). Otherwise it starts in the clone and is told to make its own worktree with `EnterWorktree`, never `git worktree add`, run `git checkout --detach <head>` in it, and leave with `ExitWorktree` (remove, discard_changes) after `findings-done` (`OwnWorktree`). Reasons: the tour agent's folder may stand on another branch or hold changes, so the review would read the wrong code and pin findings to the wrong head; and the maintainer's projects have a hook on Claude Code's worktree creation that makes a cheap worktree that works, which git's plain one does not run. The agent writes no reviewed code either way. `check-findings` pins an unpinned file to HEAD of the folder it runs in, the reviewed head in both cases.
- In `OwnWorktree` the tool list has no `Read` rule for the folder, since the hook decides where the worktree is and the session reads its own working folder. The app makes and removes no review worktrees; the start-up sweep still removes those of older builds. Open: an agent killed before `ExitWorktree` leaves its worktree to the hook's own clean-up.

## One window

- One window that every CLI command reuses (2026-11-06). `AppWindow` (viewer) says what each event does to the window's handle; requests that reach a PR (`AgentReplied`, the reopen after Save, a reload) only get the review window.
- The window may hold only Settings (2026-11-10, issue #13): `guided-review settings` sends `show_settings` to the app, starting it as `open` does. With no PR the app opens one window with only Settings (`SettingsWindow`), no sidebar. A later `open` turns it into the review with `replace_root`, and the panel moves over with whatever is being edited. Save there writes the config and closes the window; so do Close, Esc and the red button, after the unsaved-changes question. Closing the Settings-only window quits unless an `open` is building (`ActivePr::is_building`); then the app stays with no window and the build opens one. A failed build with no window opens the switcher with the reason under the query (`FailedBuild::OpenSwitcherWithReason`, 2026-11-17, see [local review](local-review.md)). A failed build while only Settings shows puts its reason under the Settings title. Keeping the Settings window open until the build lands was turned down, as Close would then not close.
- `open` of a PR with no tour and no window opens a window holding only the loading screen (`WritingWindow`, `AppWindow::WritingOnly`); the writer's `open` turns it into the review. With the Settings-only window up, the writing is followed with no screen. A PR with no tour picked in the switcher-only window (`AppWindow::SwitcherOnly`) turns it into the loading screen (`ShowWriting::ReplaceSwitcher`). Closing the loading-screen window quits unless the finished tour is building. A written tour that fails to build puts the writing back as Failed ("The tour was written but could not be opened: ..."), with Try again and the window kept (`FailedBuild::ShowInWriting`). Settings asked for meanwhile is refused until the review is up.
- A click on the Dock icon of a running app with no window opens the switcher alone; a minimized window comes back as it was (`AppWindow::relaunched`, 2026-11-16). macOS sends a running app a reopen event, not a new launch. On Linux gpui never fires reopen; the launcher starts a new process, which hands `show_switcher` to the running app. Before this, an agent-started `open` that was kept in the background left an app with no window and a Dock icon that did nothing.
- Save in Settings reopens the PR on screen behind the Opening veil, since a saved `config.toml` only reaches a PR when it is built (`ekvedaras/guided-review@fb856ef`, `fcbda27`). The reopen swaps the window's root, and the old root owns the tasks that type hand-offs into the tour agent, so it waits until no hand-off is being delivered (`ReopenAfterSave`, `InFlight`) and the window says so under the title bar. Saving again meanwhile is still one reopen. The wait lives in the layout, so a switch to another PR ends it. An agent reply that lands while the build runs is applied to the old window and also held by `ActivePr` (`held_replies`), because the build may have read the state file before the old session saved; the new window applies the held replies again, which only sets a hand-off's state. While the reopen builds, the layout saves typing, takes focus out of the boxes and ignores navigation, wrap, jump and settings keys, so the old session saves no reviewer input after the build read the state file; the veil keeps the mouse out. Open: a reopen that finds another PR building is dropped (the build reads the new config anyway), and a failed reopen shows its reason and does not retry.

## The agent link

- `AgentLinkOff` names why the Tour agent is off (2026-11-12): `hc` missing, server not running (`hc server status` fails), or herdr running but a command failed (`HerdrFailed`, the reason herdr gave with no command line, and a hint to `hc server restart`, which may pause running terminals). The hc adapter raises `HerdrRefused` for a failed command so the viewer can take the reason out. It exists because a dead herdr registry writer once showed the wrong message and the app never looked again.
- While the link is off the work agenda holds `WorkKind::CheckAgentLink`, due `AGENT_LINK_RECHECK` (30 s) after the last news and at once on the sidebar's Retry. It runs `TourAgents::lookup`, not only `link()`, because `server status` can answer while `ls` fails. Back: `AfterLanding::TourAgentIs` makes the app follow the tour agent again. The app never restarts herdr; it only suggests it.

## A command never quits an app of another build

On 2026-11-16 a tour agent's `guided-review open`, of another build than the maintainer's running trial build, quit that app and its session. The maintainer decided: a CLI command from another build than the running app never tells it to quit. Only a start the reviewer makes ends an app of another build. Built in `src/app_link.rs`:

- A request line says whether an app of another build may act on it (`AcrossBuilds`), and a quit may name the build it ends (`replacing`). `RequestLine::is_taken_by` is the app's side: its own build always; another build's quit only when it names this build; another build's other request only when marked `any_build`. A request the app cannot read, or an unmarked one, is answered `other_build`.
- `Caller::on_other_build` is the command's side. `Command` (anything run in a terminal, by the reviewer or an agent, which cannot be told apart) stops with `OtherBuildRuns`, a message naming both builds. `Launcher` (the OS launcher, told by `launched_app_variable`) replaces the app. `AppRestart` replaces only the build named by the hidden `restart --replacing <build>`, which the app's Restart and its update pass with their own build. `restart` first asks which build runs with a request whose version is no build's.
- `restart` and `open` typed after a `cargo install` or a manual install no longer replace the running app; the reviewer quits it, or uses Restart app, which runs the binary now at the app's path.
- Open: an app from before this change runs `restart` without `--replacing`, so its update to the first release with this change installs but cannot restart into it; the reviewer quits and starts the app once. The OS launcher is told by an environment variable that the app's own children inherit on macOS; only a bare `guided-review` of theirs would count as a launch. The CLI still answers "the reviewer reads another PR" when nothing is on screen.
