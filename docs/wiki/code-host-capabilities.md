# Code host capabilities

Issue #140, 2026-11-25. The viewer's code reads and writes a code host through `CodeHost` (`src/viewer/ports.rs`). GitHub is the only adapter. `CodeHost` is shaped so a second host (GitLab is the one checked against) fits without changes in the viewer. What GitLab does is from my knowledge of its API, not checked against its docs, wherever this page says GitLab.

## Core ports and capabilities

`CodeHost` is the core ports as supertraits, plus one accessor per capability that returns `Option<&dyn Port>`.

Core, every host of PRs does it: `ChangeTipsPort`, `PullsOfBranchPort`, `PullRequestDescriptionPort` (with the title), `PullRequestOriginPort`, `PullRequestStatusPort` (status, checks, draft), `ReviewThreadsPort`, `ReviewWritesPort` (`submit_review` with no verdict, and `approve`), `RelevantPullRequestsPort` (the PRs that involve the viewer), `ClonePort` and `HostedCodePort` (see below).

| Capability | Port | Accessor | Why it is optional |
|---|---|---|---|
| Viewed marks | `ViewedFilesPort` | `viewed_marks` | GitLab keeps its "viewed" checkbox in the browser, with no API. |
| Merging | `MergingPort` | `merging` | `MergeChange` is GitHub's auto-merge shape; a host may merge only on its web page. |
| Reactions on a PR | `PullRequestReactionsPort` | `pull_request_reactions` | Bitbucket and Azure DevOps have no emoji on a PR (not checked). It only carries the reviewing mark. |
| Picture uploads | `PictureUploadPort` | `picture_uploads` | GitHub's store is undocumented ([PR notes](pr-notes.md)); another host may have none. |
| Issue tracker | `IssueDetailsPort` | `issue_tracker` | A repo's issues may live in Jira, not on the host. |
| Requests for changes | `ChangeRequestsPort` | `change_requests` | GitLab added a request-changes state to reviews only in recent versions, and a self-managed GitLab may be older (not checked). |
| Reactions on comments | `CommentReactionsPort` | `comment_reactions` | Bitbucket and Azure DevOps have no emoji on a comment (not checked). |

`NoHost`, a local review's host, returns `None` for every capability. Its core ports refuse, since each takes a PR URL a local review does not have.

### Why ports and not a flag list

A flag list beside the ports (`supports_viewed_marks: true`) can disagree with them: the flag says yes and the port does nothing, or the other way. An optional port cannot: the host has the port or it does not, and the work that uses it reaches it only through the `Option`. Work for a capability the host lacks fails with `HostError::NotOffered(Capability)`, which the review never asks for. It is not `NoAccess`, which says the token is missing or refused. Viewed sync settles it as it settles `NoAccess`: sync goes off for the session and the banner names the missing capability.

### How the review learns it

`Capability` (`src/viewer/capability.rs`) names each one, and `HostCapabilities` is the set a host offers. `HostCapabilities::of(&dyn CodeHost)`, beside `CodeHost` in `ports.rs`, reads each accessor once. `Review::open`, `Review::open_basic` and `ReviewBuilder::new` take it, so no review is built without its host's capabilities. Each part that shows a capability is built from the set, so none shows one by default: `ViewedSync::for_host`, `ReviewingMark::new` (finished from the start with no reactions), `PrControls::of` (no merge button, `Shift+M` or palette action), `PrNotes::for_host` (no note that shows a picture), `RelatedIssues::of` (no hover details), `CommentDesk::for_host`.

A new capability is a `Capability` variant and its name, a `CodeHost` accessor and its arm in `HostCapabilities::of`, and the part that asks `has` for it. `capability` sits below `ports` and the parts, since `ports` names the parts' value types and `HostError::NotOffered` names a `Capability`. The review's work is planned on the UI thread and run with the ports lent on another, so the review cannot hold the port; it holds what the port's absence means for each part.

`open_review` reads the set from the opened subject's host (`NoHost` for a local review, so none) and hands it to `ReviewBuilder`, `TourRefresher`, `TourReloader`, `TourSwitcher` and `TourRepinner`, which rebuild the review on re-pin, refresh, reload and switch to guided. The session's snapshot staging reads it from its own host. Nothing tells a review afterwards. Tests pass `support::fake_ports::every_capability()`, or `HostCapabilities::of(&host.without(..))` when the test is about a host that lacks one. Before this, a local review offered every capability and counted its ticks as unsent viewed marks (`opened_subject::a_local_review_opened_as_the_app_opens_it_offers_no_host_viewed_marks`).

### What a missing capability does

- **Requests for changes.** `ChangeRequestsPort::request_changes` is not core. On a host without it `Review::can_request_changes` is false, `finish_review_request` refuses with `FinishRefusal::NotOffered` before anything is sent, and the finish form shows only Comment and Approve (`Finishing::CommentOrApprove`). `ReviewVerdict` is the reviewer's choice in the finish form and lives in `finish_review`; `FinishRequest::run` turns it into the port call. GitHub's event names (`COMMENT`, `APPROVE`, `REQUEST_CHANGES`) are the adapter's private `ReviewEvent`. GitLab's approval is a call of its own, so its `approve` would publish the draft notes and then approve (not checked).
- **Reactions on comments.** `CommentReactionsPort::set_comment_reaction`. On a host without it a hand-off puts no seen mark and is delivered all the same (`SeenMark::Off`, no trouble named), the thread shows no reactions to add (`Review::can_react_to_comments`), and a reaction asked anyway is refused with `CommentRefusal::NotOffered` before the host is asked. `DeliveryRequest`, `AgentReplyRequest`, `SeenMarkOff` and `ThreadActionRequest` run with a `&dyn CodeHost` and reach the port through its `Option`.
- **Merging.** `MergingPort::pull_request_merging` gives how a PR would merge (merge state, auto-merge, merge methods, what the viewer may do). The status job reads the status, and only for an open PR on a host with a merging port, how it would merge (`Done::PrStatus { status, merging }`). GitHub reads the two in two queries, one more request per status read (every 30 s while checks run). `PrControls` keeps the merging state apart from the status, only when the review offers merging. A GitLab adapter would fill it from `detailed_merge_status`, `merge_when_pipeline_succeeds`, the project's merge method and squash option, and the user's merge permission (not checked). Approvals are not in it; they would be a capability of their own.

### PrControls

`PrControls` keeps `merging` to itself (`None` on a host with no merging), which made deslop-please report two field leaks. They are fixed, not allowed:

- `PrControls::status_is` says when to read the status again (while checks run); `ReviewCore::pr_status` hands out a copy, not a borrow. The copy costs one reference count: `PrStatus` is plain values and an `Arc<[CheckRun]>`. The title bar cannot hold a borrow: it reads the status from the session and then lends `cx` mutably to build its buttons.
- The merge method is the reviewer's setting, not the PR's state: `ReviewCore` holds it (`read_merge_method_from(&Config)` picks the PR repo's method) and passes it to `PrControls::ask_to_change_merging`.

On a rebuild (re-pin, refresh, reload, switch to guided) the new review takes the replaced one's PR controls through `PrControls::carry_on_from`, which keeps whether merging is offered from the new build. Assigning the replaced controls whole kept the old build's answer (`pr_controls::a_reopened_pr_review_offers_merging_as_its_own_build_says_whatever_the_replaced_one_offered`).

## Host contract

`tests/it/host_contract/` holds shared cases per port, each written once over a builder that makes a host holding a given PR (`PullOnHost`: title, description, author, branches and fork, tips, status, merging, closing issues, reviews, a web pending review, code, viewed files, threads, and whether the host answers). `every_case_for!` runs every case against `FakeHost` and the GitHub adapter. GitHub runs against `github_api.rs`, which answers GitHub's GraphQL API and the REST calls the adapter makes for one PR held in memory, in GitHub's shapes, two nodes a page, never the network. `capabilities.rs` checks that GitHub offers every capability and `NoHost` none, and that `NoHost` refuses to clone. A new host gets a builder in `hosts.rs` and one more name in `every_case_for!`.

Every port of `CodeHost` and every capability port has cases, including one for a host not answering, and for the GraphQL ports one for no token. The cases are grouped by what they are about (`pull_request/`, `review/`, `repo/`), since one folder of 18 files was wider than deslop-please allows.

Rules the contract fixed in the fake, to match GitHub:

- `FakeHost` fails as GitHub does. `ConnectionLost` is `NotAnswering(GitHub, NoConnection)` ("GitHub is not answering (no connection)"), not a plain `Other`. `HostFault::NoToken` refuses what needs a token on GitHub: the GraphQL calls. Tips, title, description, head branch, pulls of a branch and code, read over REST, answer as for a public repo (`a_public_repos_pr_and_code_read_without_a_token`); a private repo without a token is not modelled.
- Faults that model a failure that is no outage are `ReadsAnswerAnError`, `ThreadReadsAnswerAnError`, `ViewedPushesAnswerAnError` and `RelevantListAnswersAnError`. They fail with `fake_ports::HOST_ERROR`, the error GitHub answers a GraphQL call it could not run, with HTTP 200. An outage stays `ReadsFailWith` and `ConnectionLost`.
- A reply to a thread the PR does not have is refused. A reaction taken off a comment leaves no count of 0. An upload that is no picture, or that cannot be read, is refused before anything is sent. `FakeHost::with_title` sets the title.
- New threads read back: `FakeHost` and `github_api.rs` list a thread made by `add_review_thread` or `comment_now` with the viewer's comment at its place. `FakeHost::naming_new_threads` names it when a test refers to it, and `HostFault::NewThreadsUnlisted` stands for a host that has not listed it yet. The adapter's query asks no comment state, so a pending thread reads like a posted one. That GitHub lists a thread of a pending review to its author is from the app's own use, not checked against GitHub's docs.
- A comment or reply posted now is the viewer's last review on both hosts (Commented, no body, at the head), and a sent review stands as the viewer's in the standings in place of their review request.
- `GitHub::comment_now` looks for a pending review first and refuses with `PendingReviewExists`, one more request per comment posted now. GitHub adds a thread with no review id to the viewer's pending review (not checked against GitHub's docs; it is how the app's own Add to review behaves), so without the look-up `comment_now` sent the reviewer's whole pending review. The app offers Comment now only with no pending review, so only one started on the web in between met it.
- `GitHub::cloning_with(program)` is the seam for the `gh` that clones (`gh` on `PATH` by default), so the contract runs a stand-in `gh` with no change to `PATH`. `FakeHost` clones as `gh` does (`git init` and an origin on github.com).

## Web addresses, clones and code behind the host

- `PullRequestUrl` is the neutral PR identity and carries `host: HostSite`, read from its link. `HostSite::GitHub` is the one host (`HostSite::ALL`); `HostSite::name` is the word the UI shows, `HostSite::key` the key in config text.
- `host_web` is a PR's host on the web: the PR's page (`PullRequestUrl`'s text form, so its subject key), its checks page, the ref its head is fetched by, a file at a commit (`HostSite::file_page`, `file_of_link`), how the host writes a reference to the PR in text (`PullRequestUrl::short`: GitHub's `owner/repo#7`; GitLab would write `group/project!7`) and the repo a git remote points at. Each is a `match` on `HostSite` that asks the host's own shapes, so a second host is a compile error at every place it must answer.
- `github_web` is GitHub's shapes. It takes and gives a PR's parts (repo, number), not `PullRequestUrl`: when it built and read `PullRequestUrl` while `PullRequestUrl`'s text form asked it, deslop-please reported a tangle. It is a top-level module, not `github::web`, since `github` sits above `viewer` (it implements the viewer's ports) and these shapes sit below it (`viewer::code_link` reaches them through `host_web`). `url_path` percent-encodes a path in a link.
- A link of a host the app does not read is refused naming the hosts it reads ("not a PR link of a code host guided-review reads (GitHub): <link>").
- **Cloning is a core port**, `ClonePort`: every host's repos can be cloned. GitHub clones with `gh repo clone`; `NoHost` refuses, since a local review reads its own folder. The session clones through the review's host.
- **Code is read through a core port too**, `HostedCodePort::code_of(repo)`: every host serves a file at a commit, the diff between two commits and their merge base (GitLab: its repository files and compare APIs). `pick_code_source` takes the port and owns why the host's code is read though a clone was found (its fetch failed), so no adapter carries a fallback reason. `NoHost` refuses.
- `opened_subject::hosts` is the one place a `HostSite` becomes its adapter: `adapter_of`, `host_of(&ReviewSubject)` (a PR's adapter, or a local review's `NoHost` looking up its branch's PR on its origin's host, none with no origin), and `EveryHost`, which routes look-ups by the repo's or PR's host and lists the switcher's PRs from every `HostSite::ALL`, merged by `RelevantPullRequests::merged`: newest first, a host that fails left out, failing only when every host does, since a reviewer need not have an account on each.
- Only the release downloaders (`app::updater`, `app::language_servers`) make `GitHub::from_env()` outside the adapter and `opened_subject::hosts`: guided-review's and the language servers' releases are on GitHub whatever host a PR is on.

What fits GitLab: an MR's page (`.../-/merge_requests/7`), its head ref (`refs/merge-requests/7/head`), its pipelines page and a file at a commit (`.../-/blob/<sha>/<path>#L12`) each fit a `host_web` method, and a clone fits `ClonePort::clone_repo(repo, folder)`. Two things needed a change: a project path has any number of groups (see the next section), and a self-managed GitLab is its own site, so `HostSite` would carry its address and the hosts the app reads would come from the config, not `HostSite::ALL`.

## A repo is a path, and is keyed by its host

- `RepoName` is a namespace of one segment or more and a name, read from `namespace/name` split at the last `/`, every segment non-empty (`owner()` is `namespace()`), since a GitLab project path is `group/sub/project`. GitHub's form is the same text, so every persisted form of a GitHub repo is unchanged. A GitHub issue reference (`owner/repo#12`) reads only GitHub's two segments (`github_web::repo_named`), so `a/b/c#12` names no issue.
- `HostedRepo` (`pull_request.rs`) is a host and a repo. `HostedRepo::of_remote` reads both from a git remote, `None` for a host the app does not read. A local change set's `origin` is one, and a local tour's pin keeps its `host` beside `repo` (a pin without one is GitHub's, the only host the app read before). `PullsOfBranchPort::open_pull_of_branch` takes a `HostedRepo`, so a caller holding every host can route each look-up.
- `HostedRepo` has a text form, `<host key>:namespace/name`, and a bare `namespace/name` is GitHub's. So every `[clones]`, `[merge_methods]` and `[language_servers]` key written before reads as GitHub's, and a GitHub repo is still written bare (`clone_offer::a_clone_of_a_github_repo_is_saved_under_its_owner_and_name_as_before_hosts_were_named`). `HostedRepo`'s `Display` is a `match` on the host, so a second host writes its key.
- `LocalGit::find`, `configured_clone`, `Config::clone_of`, Settings' clone rows and the clone offer take a `HostedRepo` and accept only a remote of that repo on that host. The clone offer's line names the host the code comes from.
- The state and tour folders of a PR (`ReviewSubject::files_folder`), `Codebase` (`Codebase::Hosted(HostedRepo)`: the language servers' answer, server checkout and server index) and `[merge_methods]` are keyed by `HostedRepo`. `HostedRepo::files_folder` is the one place a repo becomes a folder, GitHub's `<owner>/<repo>` as before, so nothing on disk moves. `HostedRepo::of_files_folder` reads a folder back, and `folders_opened_from_any_repo` walks the state folder down to each folder it reads as a repo. A second host's folders go under `_<host key>/`: GitHub owners cannot start with `_`, as `Codebase`'s `_folders` already counts on.

## Names of the host

- **The UI names the PR's host** by `HostSite::name` (and `HostSite::open_on`, "Open on GitHub", where a label must be `&'static str`), or says it in neutral words where no PR is at hand (Settings, the shortcuts sheet, the CLI's subject error, the merge and comment refusals, "No access to the PR's host", "Comment posted"). The palette's Open on and Open checks on carry the host (`PaletteAction::OpenOnHost(HostSite)`, `OpenChecksOnHost(HostSite)`). The `[keys]` name is `open_on_host`; `Command::former_config_name` keeps `open_on_github` read, the new name wins when both are written, and a key set in Settings drops the old entry. The title bar's button and the host station are named after the PR's host (`Station::of_host`). An outage names the host that does not answer (`HostError::NotAnswering(HostSite, OutageCause)`, `Outage::host`; `Problem::CodeOnHost(HostSite, reason)`). The switcher names every host the app reads (`HostSite::all_named`).
- **The agents' prompts name the subject's host** (`ReviewSubject::host_name`: the PR's host, or a local change set's origin's, else "the code host"): "never post on GitHub" in the review brief, "nothing goes to GitHub" in an Ask, "GitHub markdown" in a hand-off.
- **GitHub's names live in the adapter.** The parsing and writing of GitHub's GraphQL names for check states, mergeability, review outcomes, issue states, reactions and merge methods are functions of `github::names` over the viewer's types, which know none of GitHub's words. Identifiers in generic code that mean the host say host: `ReviewersOnHost`, `host_id!` (thread and comment ids are opaque to the viewer), `RelatedIssues::host_says`, `post_on_host`. `DIFF_CONTEXT_LINES` and `is_in_pr_diff` keep GitHub's rule of 3 context lines (GitLab's diff takes comments on the context lines it shows too, not checked). The state file keeps its section names `viewed_on_github` and `github_baseline_due` (`#[serde(rename)]`, `viewed_sync::the_hosts_viewed_marks_keep_the_section_names_written_before_hosts_were_named`). The avatar download is the app's `PublicAvatars` (`app::avatar_pictures`), not the adapter's, since a comment's avatar address comes from whatever host the comment is on.
- **GitHub's name stays in generic code on purpose** in `HostSite::GitHub` and the matches on it, `opened_subject::hosts`, `IssueLink::GitHub` and `IssueUrl` (a GitHub issue is GitHub's), the release downloaders, and the default host of a pin or key written before hosts were named. Doc comments keep GitHub where they state GitHub's own rules: closing keywords, its markdown and what it hides, its time format, which review counts, the order of reactions and merge methods, `thread: null`, the release check.
