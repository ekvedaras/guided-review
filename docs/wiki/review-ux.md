# Review UX

How the app leads a reviewer through a tour, beyond its look (the look is "Ink & Trail", built on the `impeccable-ui` branch).

On 2026-11-10 the maintainer asked for UX, not only style, and approved bolder changes of behaviour and layout. What changed and why:

- **One table of shortcuts.** `viewer::Command` holds every key the app answers, with its keys, its scope and the line the shortcuts sheet shows. `app::bind_keys` binds from it with one exhaustive match, and the sheet (`?`) reads the same table, so a key cannot be bound without being listed. Main buttons show their key caps from it. The three hint lines at the foot of the sidebar went; the sheet replaces them. New keys: `n` (next unread step), `m` (mark the step read or unread), `?` (the sheet). The palettes' arrows and return stay their own `on_key_down`, named in their footers. Commit 8d3baef.
- **Actions in the palette.** cmd+k lists places under Steps, Files and Symbols, the group with the best match first, then Actions that match by name; a query that starts with `>` lists only actions. An action does what its button or key does; its key cap shows when it has one. Why: reviewers reach for one box for both going and doing (Raycast, Linear). Commit 8d3baef.
- **One gap row.** The two stacked "Show more lines" rows between changes became one row that says how many lines are hidden, with up, down and show-all buttons (`viewer::HiddenLines`). Show-all adds the hidden count to one side's context. The end of a file keeps one direction and no count: the shown lines do not tell how long the file runs on. Commit 8d3baef.
- **The summary is a start page.** Counts the review truly has (steps, files changed, added and removed lines, open threads; no time estimate), the summary, the route of top-level steps with their why, read mark and check flag, and one lead: Start the tour, Continue at the first unread step, or, once every step is read, finish. Commit 283aa9f.
- **A finish moment.** Once every step is read, the last screen's footer and the summary's lead are a success card with Finish review, which opens the sidebar's form with the keys in its body. Where the PR takes no review (the viewer's own PR with nothing to send) the card says the tour is read and offers no button. Commit 283aa9f.
- **Toasts** (`viewer::Toasts`, drawn by `toast_stack`) for outcomes that were silent or easy to miss: a comment or reply added or posted, a thread resolved or unresolved, a review sent, Settings saved, lines copied, and a problem that was not there before. They leave after four seconds unless the pointer rests on the stack, three at most; failures stay until dismissed. A queued comment, an edit and a reaction show in place and get no toast. No failure toast has a try-again: the existing try-again controls are all in place where the failure shows. The shelf lives in a global so the toast of a Save survives the reopen that follows. Commit 283aa9f.
- **Settings is a sheet over the whole window** when a PR is open: the tour sidebar is under the scrim, not live beside it, and the palette, the switcher and the shortcuts sheet wait while it is open. Esc, the close button and a scrim click go through `request_close`, which asks before discarding. This removed the 2026-11-10 rule from da86e6a that a sidebar click while Settings is open closes it and goes there, asking first when unsaved: it had no trigger left, so `go_from_sidebar`, `ask_before_leaving` and the panel's after-discard callback went. The Settings model and its tests did not change. The Settings-only window still shows Settings as its whole page, with a pinned header. Commit 283aa9f.

On 2026-11-12 every overlay learned to leave. The palette, the PR switcher, Settings, the shortcuts sheet, the Ask panel and the zoomed picture each keep a `viewer::Presence`, which says open, leaving or gone. Closing keeps the overlay drawn for `OVERLAY` while it plays the reverse of its entrance (`motion::sink_out`, `slide_out`, the scrim's `fade_out`), then drops it; reduced motion drops it at once. `overlay::close_presence` is the one place that starts the timer, and a ticket names each leave so a reopening cannot be ended by an earlier leave's timer. Input is refused by the viewer rule (`is_open` is false while leaving, so `close` and the toggles act on the next opening) and by `overlay::input_blocker`, a mouse-taking layer over a leaving panel. Why one `Presence`: the zoom had its own stage machine since 155ca4f, and five more copies of it would have drifted. The move is one timeline from 0 (gone) to 1 (in) that `Presence` keeps as data (`Stretch`: from, to, time left): opening travels it forward, leaving backward (so a leave is the entrance in reverse, `motion::along`), and a switch of direction midway continues from the position reached and takes only the time left. The Ask panel's room (its width) travels the same timeline, so the page glides narrower as it opens and wider as it leaves; the page lays out again each frame of it.
- 2026-11-17, #94, PR status in the title bar (superseded below on the same day for the chip's words and the checks, which are now listed; the rest holds) (maintainer, 2026-11-16, and the agent's choices for the rest): the PR icon is green for a ready PR and grey for a draft or while GitHub is unread; a chip beside the PR number says "Draft" or "Ready" and, when the repo runs checks, their rolled-up state (`statusCheckRollup.state` of the head commit: SUCCESS passing, FAILURE and ERROR failing, PENDING and EXPECTED running; none run is left out), tinted by the checks. No single check is listed: the palette's "Open checks on GitHub" goes to GitHub for that. Clicking the chip is the `D` key, so it too needs a second click within 10 s. The status read is `PrStatus` (`viewer::pr_status`) with `viewer_may_change_readiness` beside it, from `PullRequestStatusPort`; GitHub's `viewerCanUpdate` stands for "author or write access".
- 2026-11-17, #95, auto-merge (maintainer's decisions in the issue's 2026-11-17 comment; the rest the agent's): the same status read carries `Merging` (`viewer::merging`): `autoMergeRequest.mergeMethod`, `mergeStateStatus` with `state` (`Mergeability`: CLEAN, UNSTABLE and HAS_HOOKS merge now; every other open state is blocked, UNKNOWN included; merged or closed is not open), the repo's allowed methods and `autoMergeAllowed`, `viewerCanEnableAutoMerge` / `viewerCanDisableAutoMerge`, and `viewerPermission` ADMIN, MAINTAIN or WRITE standing for "may merge". `Merging::offer` picks one: turn off while on, Merge now while nothing blocks, else turn on. A button beside the status chip says "Auto-merge", "Auto-merge on" (pressed, with the method) or "Merge now", shows the `Shift+M` cap, and is hidden when `offer` refuses. The merge method is a Settings section (Merge commit, Squash, Rebase; a merge commit writes no key) and `[merge_methods]` in `config.toml` sets one per repo, read by `Config::merge_method`; Settings edits only the global one, since a per-repo list in Settings is more than the issue asked (open). A value that names no method reads as the default and is not a Settings problem. Snapshot scenes `63-title-bar-draft-checks-running` to `67-title-bar-merge-now`.

- 2026-11-17, #94, the chip and the checks, reworked after the maintainer found "Ready · checks failing" too many words (supersedes the chip's words and "No single check is listed" above): the chip says only "Draft" or "Ready". The checks are its tint plus a small icon (a tick passing, a cross failing, a clock running, none when the repo runs none), so red and green do not have to be told apart by colour. `PrStatus::description` still holds the old sentence ("Ready · checks failing") for anything that wants words. Hovering the chip opens a list under it (`PrStatus::check_list`): each check by name and state, failing first, then running, then passing, in GitHub's order within a state, at most `CHECKS_SHOWN` (20) with "and N more on GitHub" past that. A click opens the check's run (`Intent::OpenCheck(place)`: the check run's `detailsUrl`, or the commit status's `targetUrl`); a check with no page, or the "and more" row, opens the PR's checks page. The list is the head commit's `statusCheckRollup.contexts` (first 100), read in the one status query; a check run is running until it completes and then passes on SUCCESS, NEUTRAL or SKIPPED and fails otherwise (cancelled and timed out included); a commit status passes on SUCCESS, fails on FAILURE and ERROR, else runs. The list stays while the mouse is on the chip or on the list (`ChecksHover`), so it can cross the gap; no timer. gpui's tooltips cannot be clicked, so this is a deferred, anchored box, not a tooltip, and the chip's old "Click twice" tooltip went (the first click's toast says what the second does). gpui has no accessibility labels yet, so the description is not exposed to a screen reader (open). Snapshot scene `68-title-bar-checks-list`.
- 2026-11-18, #132 and #134 (supersedes "passes on NEUTRAL or SKIPPED" above): a check row says what GitHub says, so `CheckState` has `Neutral` and `Skipped`, muted, listed after passing. The chip's tint stays GitHub's roll-up (`Checks`), which never counted them as failing, so no parser decides "not failing" any more. `PrStatus` is now the PR state first: `Open(OpenPrStatus)`, `Merged` or `Closed`. Readiness, checks and merging live only in `OpenPrStatus`, so a merged PR cannot carry a draft flag or offer a merge, and `Mergeability::NotOpen` and `MergeRefusal::NotOpen` went. A merged or closed PR shows one chip where the status chip and merge button were (`Merged` in the accent colour, GitHub's purple; `Closed` in danger red), and `D`, `Shift+M` and the palette do nothing, with no toast, as the issue asked. A merge from the app shows `Merged` at once, before GitHub is read back. Snapshot scenes `72-title-bar-merged` and `73-title-bar-closed`.
- 2026-11-18, #142: an `open` that builds a review brings the app to the front when the request comes, not when the review is built (`AppWindow::show_building`). - 2026-11-19, a re-review that could not end (maintainer's report and picks; the rest the agent's): a re-pin takes the tick of a step whose pieces changed, and the forward key ticks a step only once its end was seen, so a reviewer could pass one unread and reach the end at 16 of 17 with no way on: the last footer said "Finish the review in the sidebar" and led nowhere. The last screen's footer now leads back with Continue at the first unread step (`N`) and says how many are unread; Next itself still never ticks unseen code. A re-review with nothing new to send ends with **Mark done** (maintainer: primary, local only, saved at the tour's head so new commits undo it, 👀 off) and **Approve again** beside it (one click, the unread warning asks once). The 👀 also comes off whenever the review closes, on quit (the app waits up to 2 s for GitHub, then quits anyway) and on a switch to another PR (`Review::close`). The small "Your last review" line became the sidebar's reviews: the reviewer's own standing as a callout in its state's colour (green approved, red changes requested, amber waiting, neutral otherwise) with an amber line while the PR has new commits and a tick once marked done, then the other reviewers by name and state (`Standing`, from GitHub's `latestOpinionatedReviews`, `latestReviews` and `reviewRequests` in the one reviews query, so an approval outweighs a later comment and the PR author answering threads is left out). Snapshot scenes `77-re-review`, `78-re-review-done`, `79-tour-end-unread`. Known open: a reviewer both asked again and holding a review shows the review, not "asked again".

Also on 2026-11-12: `g` opens the PR on GitHub (page scope, like the other single letters, shown on the title bar's GitHub button) and cmd+q quits. cmd+q has the new `KeyScope::App`, bound with no key context and handled by a global action, so it works from the Settings-only window too; the macOS app menu holds the Quit item that shows the key. With an Ask answering or a hand-off being sent, cmd+q, cmd+w and Restart share one guard (`RestartGuard::ask_to`, maintainer's call 2026-11-12): the first press shows a toast saying what would be lost, and the same press again within ten seconds goes ahead; another way out does not confirm it. With nothing in flight they act at once. The review's window answers cmd+q first so it can guard; the global action only serves a window with no review.

Known open: hover and live motion were checked only in still pictures (`scripts/snapshot` runs with reduce motion); the sticky step bar's slide and the toasts' rise were not seen moving.

- 2026-11-20, #154, the primary comment action (maintainer's decision in the issue; the rest the agent's): Settings has a Comments section with **Primary action**, Add to review or Comment now (`primary_comment_action` in `config.toml`, `viewer::PrimaryCommentAction`). - 2026-11-20, #154, Primary and Secondary pickers (maintainer's decision; supersedes the note above, which stands for how a `[keys]` entry wins and how a local review reads the choice; the rest the agent's): Settings → Comments has two pickers, **Primary** and **Secondary**, each any of Add to review, Comment now, Suggest change, Ask agent, Ask agent now (`primary_comment_action` and `secondary_comment_action` in `config.toml`, `viewer::SendAction`, `SendChoice`).   - Keys: the primary has `Cmd+Enter`, the secondary `Cmd+Shift+Enter`; an action in neither keeps its own key, which no main key can take: Add to review `Cmd+Alt+A`, Comment now `Cmd+Alt+Enter`, Suggest change `Cmd+Alt+S` (new, `Command::SuggestChange`), Ask agent `Cmd+Alt+G`, Ask agent now `Cmd+Alt+Shift+Enter`.
