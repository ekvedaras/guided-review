# Review UX

How the app leads a reviewer through a tour, beyond its look (the look is in [Visual design rules](visual-design.md)). On 2026-11-10 the maintainer asked for UX, not only style, and approved bolder changes of behaviour and layout.

## Shortcuts, palette, lists

- **One table of shortcuts.** `viewer::Command` holds every key the app answers, with its keys, its scope and the line the shortcuts sheet shows (`?`). `app::bind_keys` binds from it with one exhaustive match, so a key cannot be bound without being listed. Main buttons show their key caps from it. The palettes' arrows and return stay their own `on_key_down`, named in their footers. Keys the reviewer can change: [Keys and the focused change](keys-and-focus.md).
- **Actions in the palette.** `Cmd+K` lists places under Steps, Files and Symbols, the group with the best match first, then Actions that match by name; a query that starts with `>` lists only actions. An action does what its button or key does, and shows its key cap. Why: reviewers reach for one box for both going and doing.
- **One gap row** for hidden lines between changes (`viewer::HiddenLines`): how many lines are hidden, with up, down and show-all buttons. The end of a file keeps one direction and no count, since the shown lines do not tell how long the file runs on.
- **One search row** (`components::search_row`): the palette's look, a search icon and the query box on a row of their own under the list's head. The files list, the comments list and the agent picker use it. In the files and comments lists `?` gives the box the keys.
- **Finding the lists.** On 2026-11-26 (#198) the maintainer found that nothing showed that `T` and `C` exist, and `C` on a review with no threads did nothing, which looked broken. Now `C` and the palette's Comments list open on every review (an empty list says "No comments yet"). The summary's and the overview's "N files changed" open the files list, their open-threads count the comments list. The sidebar's foot is one row of four icon buttons with keys and names in tooltips: Files (`T`), Comments (`C`), Settings (`Cmd+,`), Shortcuts (`?`), with the version line under them. The title bar was tried first, but at the snapshot width the buttons pushed GitHub and the issue button out of it. See [Files list](files-list.md) and [Comments list](comments-list.md).
- **`g`** opens the PR on its host. **`Cmd+Q`** quits: it has `KeyScope::App`, bound with no key context and handled by a global action, so it works from the Settings-only window too. The review's window answers it first so it can guard.
- **Quit guard** (`RestartGuard::ask_to`, maintainer, 2026-11-12): with a hand-off being sent, `Cmd+Q`, `Cmd+W` and Restart share one guard. The first press shows a toast saying what would be lost, the same press again within ten seconds goes ahead. With nothing in flight they act at once.

## Start page and finish

- **The summary is a start page:** counts the review truly has (steps, files changed, added and removed lines, open threads; no time estimate), the summary, the route of top-level steps with their why, read mark and check flag, and one lead: Start the tour, Continue at the first unread step, or, once every step is read, finish.
- **A finish moment.** Once every step is read, the last screen's footer and the summary's lead are a success card with Finish review, which opens the sidebar's form. Where the PR takes no review (the viewer's own PR with nothing to send) the card says the tour is read and offers no button.
- **A re-review must be able to end** (2026-11-19). A re-pin takes the tick of a step whose pieces changed, and the forward key ticks a step only once its end was seen, so a reviewer could pass one unread and reach the end at 16 of 17 with no way on. The last footer now leads back with Continue at the first unread step (`N`) and says how many are unread. Next itself never ticks unseen code. A re-review with nothing new to send ends with **Mark done** (primary, local only, saved at the tour's head so new commits undo it, 👀 off) and **Approve again** beside it (the unread warning asks once). The 👀 also comes off whenever the review closes: on quit (the app waits up to 2 s for GitHub, then quits anyway) and on a switch to another PR (`Review::close`).
- **The sidebar's reviews** show the reviewer's own standing as a callout in its state's colour (green approved, red changes requested, amber waiting, neutral otherwise) with an amber line while the PR has new commits and a tick once marked done, then the other reviewers by name and state (`Standing`, from GitHub's `latestOpinionatedReviews`, `latestReviews` and `reviewRequests` in the one reviews query, so an approval outweighs a later comment and the PR author answering threads is left out). Open: a reviewer both asked again and holding a review shows the review, not "asked again".

## Toasts

`viewer::Toasts`, drawn by `toast_stack`, for outcomes that were silent or easy to miss: a comment or reply added or posted, a thread resolved or unresolved, a review sent, Settings saved, lines copied, and a problem that was not there before. They leave after four seconds unless the pointer rests on the stack, three at most; failures stay until dismissed. A queued comment, an edit and a reaction show in place and get no toast. No failure toast has a try-again: the try-again controls are in place where the failure shows. The shelf lives in a global so the toast of a Save survives the reopen that follows.

## Overlays

- **Settings is a sheet over the whole window** when a PR is open: the tour sidebar is under the scrim, and the palette, the switcher and the shortcuts sheet wait while it is open. Esc, the close button and a scrim click go through `request_close`, which asks before discarding. This replaced the 2026-11-10 rule that a sidebar click while Settings is open closes it and goes there. The Settings-only window shows Settings as its whole page, with a pinned header.
- **Every overlay leaves with the reverse of its entrance** (2026-11-12). The palette, the PR switcher, Settings, the shortcuts sheet, the files, comments and findings lists, the agent picker and the zoomed picture each keep a `viewer::Presence`, which says open, leaving or gone. Closing keeps the overlay drawn for `OVERLAY` (`motion.rs`) while it plays the entrance backward (`motion::along`, the scrim's `fade_out`), then drops it; reduced motion drops it at once. `overlay::close_presence` is the one place that starts the timer, and a ticket names each leave so a reopening cannot be ended by an earlier leave's timer. `is_open` is false while leaving, so `close` and the toggles act on the next opening, and `overlay::input_blocker` is a mouse-taking layer over a leaving panel. The move is one timeline from 0 (gone) to 1 (in) kept as data (`Stretch`: from, to, time left), so a switch of direction midway continues from the position reached. Why one `Presence`: the zoom had its own stage machine, and more copies of it would have drifted. Floating panels: [Floating panels](floating-panels.md).
- **Settings pages** (2026-11-20; the maintainer chose a list on the left over tabs at the top, since Settings keeps growing). `viewer::SettingsPage`: Agents, Code, Pull requests, Keys, About, in a 180 px list built with `picker_row_at`. The maintainer turned down a page named GitHub, to stay host-neutral, and "Remote", which in git names a link like `origin`. Only the shown page's sections are built. A page with a problem shows a red mark; a refused Save, and an opening with problems, show the first page with one unless the shown page has one (`SettingsPage::after_refusal`), so a Save is never refused for something out of sight. Opening Settings starts on Agents.

## Sending comments

Settings → Pull requests has two pickers, **Primary** and **Secondary** (maintainer, 2026-11-20, #154): `primary_comment_action` and `secondary_comment_action` in `config.toml`, `keys::SendAction`, `SendChoice`. The actions are Add to review, Comment now, Suggest change, Comment and ask agent, Comment and ask agent now, and Ask agent (the private question to the tour agent, [agent-threads.md](agent-threads.md)). The two ask actions were named Ask agent and Ask agent now until 2026-11-27; the old config values still read.

- Defaults: Add to review and Comment and ask agent. The two are never the same action: picking the other's action swaps them, and a config naming one twice reads the secondary as the default.
- Keys: the primary has `Cmd+Enter`, the secondary `Cmd+Shift+Enter`. An action in neither keeps its own key, which no main key can take: Add to review `Cmd+Alt+A`, Comment now `Cmd+Alt+Enter`, Suggest change `Cmd+Alt+S`, Comment and ask agent `Cmd+Alt+G`, Comment and ask agent now `Cmd+Alt+Shift+Enter`, Ask agent `Cmd+Alt+P`. `Command::default_chords_for(SendChoice)` is the one place that decides, and a test checks that every choice of two gives different keys. A `[keys]` entry still wins for its command; a rebound key changes the key only, the button colour follows the setting.
- Buttons: primary first and in the accent colour, secondary second, the rest neutral in table order. Every action is its own button.
- Fallbacks per box (`SendAction::resolve`): an action the box does not offer is stood in for by the nearest one it does (Comment and ask agent now by Comment and ask agent, then Comment now, then Add to review; the others by Add to review). A reply offers no Suggest change; a box with a pending review on GitHub has no Comment now; a local review offers Add to tasks (Add to review) and Send now (Comment now). The stand-in shows and answers the main key of the action it stands for. A main key also runs the stand-in where the action is not offered; a key of an action's own does nothing where the box lacks it (`Keymap::send_plan`, `send_key_runs`). When both pickers end on one action the box shows one button.
- Open: Suggest change only fills the box with a suggestion block and sends nothing, so as primary it makes `Cmd+Enter` insert that block. The maintainer may prefer it not be pickable as primary.

## PR status and merging (title bar)

- **Status chip** (#94, 2026-11-17). The PR icon is green for a ready PR and grey for a draft or while the host is unread. The chip says only "Draft" or "Ready"; the checks are its tint plus a small icon (tick passing, cross failing, clock running, none when the repo runs none), so colour is not the only signal. The maintainer found "Ready · checks failing" too many words. The chip's tint is GitHub's roll-up of the head commit's checks. `PrStatus::description` still holds the long sentence. Clicking the chip is the `D` key.
- **Checks list.** Hovering the chip opens a list under it (`PrStatus::check_list`): each check by name and state, failing first, then running, passing, neutral, skipped, at most `CHECKS_SHOWN` (20) with "and N more on GitHub". A click opens the check's run (`Intent::OpenCheck`); a check with no page, or the "and more" row, opens the PR's checks page. The list is the head commit's `statusCheckRollup.contexts` (first 100) read in the one status query. A row says what GitHub says (`CheckState` has `Neutral` and `Skipped`, so no parser decides "not failing"). The list stays while the mouse is on the chip or the list (`ChecksHover`), so it can cross the gap. gpui's tooltips cannot be clicked, so this is a deferred, anchored box. The palette's "Open checks on GitHub" opens the checks page.
- **`D`** turns a ready PR into a draft or a draft ready, pressed again within 10 s to confirm (`viewer::PressAgain`, `PressStep`; the first press's toast says what the second does). It does nothing before the host is read, and says so in a toast when the viewer may not change readiness (GitHub's `viewerCanUpdate`).
- **PR state first** (#132, #134): `PrStatus` is `Open(OpenPrStatus)`, `Merged` or `Closed`. Readiness, checks and merging live only in `OpenPrStatus`, so a merged PR cannot carry a draft flag or offer a merge. A merged or closed PR shows one chip where the status chip and merge button were (`Merged` in the accent colour, `Closed` in danger red), and `D`, `Shift+M` and the palette do nothing, with no toast. A merge from the app shows `Merged` at once.
- **Auto-merge** (#95, maintainer's decisions in the issue). The same status read carries `Merging`: the merge method, `Mergeability` (CLEAN, UNSTABLE and HAS_HOOKS merge now; every other open state is blocked, UNKNOWN included), the repo's allowed methods and whether auto-merge is allowed, and the viewer's permission. `Merging::offer` picks one: turn off while on, Merge now while nothing blocks, else turn on. A button beside the chip says "Auto-merge", "Auto-merge on" (pressed, with the method) or "Merge now" and is hidden when `offer` refuses. `Shift+M` does the same, pressed again within 10 s; the first press's toast names the method and says so when the repo does not allow the reviewer's. `Shift+M` and not `M`, since `M` marks a step read and a merge weighs more. The merge method is a Pull requests setting (Merge commit, Squash, Rebase; a merge commit writes no key) and `[merge_methods]` in `config.toml` sets one per repo (`Config::merge_method`). Settings edits only the global one (open: a per-repo list in Settings is more than the issue asked). A value that names no method reads as the default.
- **A merge in flight** (#173, 2026-11-20): from the confirming press until GitHub answers (`Review::merge_in_flight`), the button is a chip in the accent colour saying "Merging" (or "Turning on auto-merge" / "Turning off auto-merge") and further presses do nothing, so a second click cannot send it twice.
- **Merge now that GitHub refuses** (#198, 2026-11-26): right after a PR was marked ready, `mergeStateStatus` said CLEAN while a ruleset still expected a required check, so Merge now was refused with an `UNPROCESSABLE` error. Those errors are now `HostError::Refused` in GitHub's own words, one line. A Merge now refused that way sends Enable auto-merge with the same method instead (`PrControls::turn_auto_merge_on_instead`) where the repo allows auto-merge; in a repo without it the refusal is the problem. The in-flight chip says what happened, so no toast.
- An `open` that builds a review brings the app to the front when the request comes, not when the review is built (`AppWindow::show_building`, #142). An open the app keeps in the background (an app-started agent's) raises nothing.

## While a guided tour is written

The sidebar shows one agent line, not two (#153). The stage ("Guided tour: the tour agent is writing it", or "waits for you in its terminal") carries the one Show agent and, under it, the last step line the agent printed (`GuidedTourStage::activity`, from `TourWriting::screen`). The separate "Tour agent: working" row is hidden meanwhile (`Review::shows_tour_agent_line`). The line does not name the terminal id, which means nothing to a reviewer. The tour is written by an interactive agent in a herdr terminal, where the screen read by `hc read` is the only source, so `TourWriting::latest_step` takes the latest line led by `•`, `⏺` or `●` and shows its text only. Spinner lines, `⎿` tool output, the prompt box and the status bar are skipped; with no step line yet the stage shows none.

## Text that can be copied, and accessibility (#198, 2026-11-26)

- `SelectableText` and `InlineMarkdown::selectable` make a body join the prose selection, so problems, toasts, the loading screen, thread error lines, the composer, Finish review, the sidebar, Settings, summary and overview titles, step titles (unless a click folds it), check and TL;DR lines and an issue card's title can be copied with `Cmd+C`. Rows that act on a click (step labels, palette rows, list rows, footer, route stops, the title bar's PR title) take no selection, since a press there must not start one. The title bar's branch names stay unselectable as the bar moves the window. The Settings window has its own key context, `SettingsWindow`. The switcher and writing windows still copy nothing (open).
- The pinned gpui reports elements to macOS through AccessKit, but only one with an element id and a role, so Homerow and VoiceOver found nothing to press. Clickable elements now carry `.role(...)` (Button, Link, Tab, CheckBox) and an `aria_label`; text boxes are text inputs. The chip's long description is not exposed to a screen reader (open).
